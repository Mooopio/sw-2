1. Monolithic Architecture

Definition

A monolithic application is a single-tiered software application in which the user interface and data access code are combined into a single program from a single platform.

It is self-contained and independent from other computing applications. The design philosophy is that the application is responsible not just for a particular task, but can perform every step needed to complete a particular function.

🏗️ How a Monolith Works — The Hospital Analogy ▼

The slides use a Hospital OPD (OutPatient Department) as the example for transitioning from monolithic to microservices.

In a monolithic hospital system: the entire patient journey — registration, doctor consultation, lab tests, pharmacy, billing — all lives inside one massive application. One failure (say, the billing module crashes) could take the whole system down.

In a microservices hospital system: Registration, Consultation, Lab, Pharmacy, and Billing are each separate independent services with their own data stores, deployable independently.

2. Microservices — Definition & Characteristics

Core Definition

Microservices are small, independent, and loosely coupled services. A single small team of developers can write and maintain a service.

10 Key Characteristics

1. Separate Codebase per Service Core ▼

Each microservice is a separate codebase that can be managed by a small dedicated development team. No single massive repository holds everything.

2. Independent Deployment Critical ▼

Services can be deployed independently. A team can update an existing service without rebuilding and redeploying the entire application. This is perhaps the biggest operational advantage.

Analogy: You can replace a single engine part in an airplane without grounding the whole fleet.

3. Own Data Persistence Core ▼

Services are responsible for persisting their own data or external state. This differs from the traditional model where a separate shared data layer handles all data persistence.

⚠️ Exam Trap: This is why data consistency becomes a challenge in microservices — each service owns its own database, so cross-service consistency is hard.

4. Well-defined API Communication Important ▼

Services communicate with each other using well-defined APIs. The internal implementation details of each service are hidden from other services (encapsulation at the service level).

5. Polyglot Programming Support Key Feature ▼

Microservices support polyglot programming. Services don't need to share the same technology stack, libraries, or frameworks. Service A can be Python + PostgreSQL; Service B can be Node.js + MongoDB.

6–10. Additional Characteristics ▼
  • Single Responsibility — each service does one thing well
  • Business Boundary — services are defined by business logic using DDD (Domain-Driven Design)
  • Function Boundary — services are bounded by development functions
  • Small team manageable — "two-pizza team" rule applies
  • Loosely coupled — changes to one service minimally affect others

3. Domain-Driven Design (DDD)

Definition

Domain-Driven Design (DDD) is a major software design approach that focuses on modeling software to match a domain according to input from that domain's experts.

Under DDD, the structure and language of software code (class names, class methods, class variables) should match the business domain. For example, a banking system should have classes named Account, Transaction, Ledger — not generic names like DataHandler.

DDD is the principle behind the Business Boundary characteristic of microservices — each microservice aligns to a specific domain (e.g., Payments domain, Inventory domain, Customer domain).

4. Benefits of Microservices Architecture

🚀 1. Faster Deployments Benefit ▼

Microservices architecture allows for faster development and deployments since it simplifies the design. Each module is easily built, tested and deployed independently, giving businesses increased agility and faster time to market.

Analogy: Rather than shipping an entire factory, you ship individual product lines — faster and more targeted.

📈 2. Scalability Benefit ▼

Offers ease in scalability since the modules work independently and each has a bounded context. The design allows fast addition of new features. With test automation, each module is tested independently and the whole system can be tested in minutes automatically.

Analogy: If your checkout service is overloaded on Black Friday, scale only that service — not the whole application.

⬆️ 3. Guaranteed Up-time Benefit ▼

With the right microservices architecture, it is almost impossible for the whole system to go down. Since each microservice is built, deployed and managed independently and is totally isolated at runtime, the whole system can never go down from a single failure.

🔓 4. No Vendor Lock-in Benefit ▼

Microservices are based on open standards backed by the open-source community. Almost all commercial microservices platforms follow these open standards, making it easy to migrate from them if needed. Standard-based APIs make it easy to extend and use different programming languages and technologies.

🛡️ 5. Resilience & Robustness Benefit ▼

Platforms are far more resilient and robust. Kubernetes or OpenShift container platforms monitor and self-heal whenever the system is affected. Orchestration capabilities can self-monitor and restart failed components. Self-healing extends from monitoring infrastructure, clusters to nodes and pods.

📌 Exam Note: Kubernetes and OpenShift are the specific platform examples given in the lecture for orchestration and self-healing.

👥 6. Dynamic Talent Pool Benefit ▼

With microservices, it's easier to onboard new team members as well as hire software engineers with different coding backgrounds. Since services are independent and can use different tech stacks, specialists in different technologies can each contribute to their relevant service.

5. Challenges in Microservices

⚡ 1. Complexity Challenge ▼

A microservices application has more moving parts than the equivalent monolithic application. Each service is simpler, but the entire system as a whole is more complex. You now manage dozens of services, deployments, and communications instead of one monolith.

🛠️ 2. Development and Testing Challenge ▼

Writing a small service that relies on other dependent services requires a different approach. Existing tools are not always designed to work with service dependencies. Refactoring across service boundaries can be difficult. It is also challenging to test service dependencies, especially when the application is evolving quickly.

🌐 3. Network Congestion & Latency Challenge ▼

The use of many small, granular services results in more inter-service communication. If the chain of service dependencies gets too long (Service A calls B, which calls C...), the additional latency can become a problem.

  • Design APIs carefully
  • Avoid overly chatty APIs
  • Think about serialization formats
  • Use asynchronous communication patterns like queue-based load leveling
🗄️ 4. Data Integrity Challenge ▼

With each microservice responsible for its own data persistence, data consistency can be a challenge. Maintaining consistency across multiple service-owned databases (distributed data) requires distributed transaction patterns that are complex to implement.

🔢 5. Versioning Challenge ▼

Updates to a service must not break services that depend on it. Multiple services could be updated at any given time, so without careful design, you might have problems with backward or forward compatibility.

🎓 6. Skill Set Challenge ▼

Microservices are highly distributed systems. Teams must carefully evaluate whether they have the skills and experience to be successful. Understanding concepts like distributed computing, container orchestration, and service mesh requires advanced expertise.

🏛️ 7. Lack of Governance Challenge ▼

The decentralized approach has advantages, but can also lead to problems. You might end up with so many different languages and frameworks that the application becomes hard to maintain. Without governance standards, teams make incompatible technology choices.

6. Communication Design

Synchronous Communication
  • A service calls an API that another service exposes
  • Protocol: HTTP or gRPC
  • Caller waits for a response from receiver
  • Also called: HTTP Communication / REST API
  • Simple; good for request-reply patterns
  • ⚠️ Risk: chain latency if many services depend on each other
Asynchronous Communication
  • A service sends message without waiting for a response
  • One or more services process the message asynchronously
  • Types: Message Communication (message broker) and Event-driven Communication
  • Better for latency-sensitive or high-volume systems

Three Communication Types

1. HTTP Communication (Synchronous) ▼

Also known as Synchronous communication. Calls between services via REST API is a viable option for service-to-service communication. The caller waits for the callee to respond.

2. Message Communication (Asynchronous) ▼

Also known as Asynchronous communication. Services push messages to a message broker that other services subscribe to. Examples: RabbitMQ, Apache Kafka.

Analogy: Like a postal system — you drop a letter (message) in a mailbox (broker), and the recipient picks it up when ready.

3. Event-Driven Communication (Asynchronous) ▼

Another type of Asynchronous communication. Services don't need to know the common message structure — they react to events. This is the most decoupled form of communication.

Analogy: Like a smoke alarm — every device reacts to the event (smoke detected) independently, without knowing about each other.

7. API Gateway

Definition

An API Gateway is a fully managed service that makes it easy for developers to create, publish, maintain, monitor, and secure APIs at any scale. APIs act as the "front door" for applications to access data, business logic, or functionality from backend services.

8. Service Discovery

The Problem

In a modern cloud-based microservices application, service instances have dynamically assigned network locations. The set of instances changes dynamically because of autoscaling, failures, and upgrades. Client code cannot simply read from a static config file to find services — it needs an elaborate service discovery mechanism.

Solution: Service Registry

A Service Registry is a database of available service instances. Services register themselves when they start and de-register when they stop. Clients query the registry to find available instances.

Three Properties of Service Discovery

⚖️ 1. Load Balanced Property ▼

Service Discovery should dynamically load balance requests across all service instances to ensure that service invocations are spread across all service instances managed by it. No single instance gets overwhelmed.

Analogy: Like a traffic controller at a toll plaza — directing cars to the least-busy lane.

🔄 2. Resilient Property ▼

The client should "cache" service information locally. Local caching allows for gradual degradation of the service discovery feature so that if the service discovery service becomes unavailable, applications can still function and locate services based on information in its local cache.

🛡️ 3. Fault-tolerant Property ▼

Service Discovery should detect when a service instance isn't healthy and remove the instance from the list of available services. This ensures clients are never directed to a failed or unhealthy instance.

⚠️ Common Exam Traps

Trap 1 — "Microservices = Simple System"

FALSE. Each individual service is simpler, but the entire system as a whole is MORE complex, not less. This is one of the core challenges (Complexity). Don't confuse part-simplicity with system-simplicity.

Trap 2 — Shared Database in Microservices

In microservices, each service has its own data persistence. They do NOT share a central database. This is a fundamental difference from monolithic architecture and the reason why Data Integrity is a challenge.

Trap 3 — Message vs Event-Driven Communication

  • Message Communication: Uses a message broker; services subscribe to it; they DO share a common message structure
  • Event-Driven Communication: Services don't need to know the common message structure — this is the key differentiator

Trap 4 — Resilient ≠ Fault-tolerant (in Service Discovery)

  • Resilient = client caches service info locally; app still works even if the discovery service itself goes down
  • Fault-tolerant = the discovery service detects and removes unhealthy service instances

Trap 5 — Lack of Governance is NOT a benefit

The decentralized nature of microservices is both a benefit (polyglot, flexibility) AND a challenge (Lack of Governance). The exam might try to confuse these. The challenge is when decentralization leads to an unmanageable mix of languages and frameworks.

Trap 6 — API Gateway is NOT Service Discovery

  • API Gateway: Entry point for external clients; manages API lifecycle (create, publish, secure)
  • Service Discovery: Internal mechanism for services to find each other dynamically

📦 Chunking — The "SILO" Model for Microservices

Think of each microservice as a SILO:

  • Separate codebase — its own repository
  • Independent deployment — deployed without touching others
  • Loosely coupled — communicates only via API
  • Owns its data — its own database
