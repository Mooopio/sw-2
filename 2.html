Phase 1

Deep Understanding

Every principle explained from first principles — with analogies, code examples, and exam-critical details.

S
Single Responsibility Principle
SRP — One reason to change
Definition: "Every software component should have one and only one responsibility — or one and only one reason to change."

What is a "component"?

A component can be a class, a method, or a module. SRP applies at all levels.

The Two Core Concepts of SRP

1. Cohesion

Cohesion is the degree to which the various parts of a software component are related. Think of it like a recycling bin system:

Analogy: An unsegregated waste bin (everything mixed together) = low cohesion. Separate bins for paper, plastic, glass = high cohesion. Each bin has one clear purpose.

SRP demands high cohesion. Methods inside a class should all be related to the same responsibility.

Example — Square class violation: A class with calculateArea(), calculatePerimeter(), draw(), and rotate() mixes two concerns: math/measurements and rendering. This is low cohesion.

Fix: Split into Square (measurements) and SquareUI (rendering). Now each class has high cohesion.

2. Coupling

Coupling is the degree of interdependency between software components. Changing one should not force changes in others.

Analogy: Different train tracks have different widths — each train is tightly coupled to its specific track. In software, tight coupling is undesirable.

Example — Student class violation: A Student class that contains MySQL database code is tightly coupled to the database. If you switch to MongoDB, the entire Student class must change.

Fix: Move database logic to a StudentRepository class. Student calls new StudentRepository().save(this). Now the Student class has only one reason to change (student profile data), and the Repository has one reason to change (database operations).

Key Rule: If two "reasons to change" are closely related (e.g., student ID format and student name format → both are "student profile"), they can be combined into one responsibility.
O
Open/Closed Principle
OCP — Open for extension, closed for modification
Definition: "Software entities should be open to extension but closed to modification."

"Open for extension" means you can add new functionality as requirements grow.

"Closed for modification" means once a class is developed, you should not modify it (except to fix bugs).

Goal: Code should be both flexible (new features are easy to add) and stable (existing code doesn't break).

How to Achieve OCP

Use abstractions (interfaces or abstract classes) instead of concrete classes. New behavior is added by creating new classes that implement the interface — without touching existing code.

Football Match Example

A Match class that contains if (Team is Ahly)... else if (Team is Zamalk)... violates OCP. Every new team requires modifying the Match class.

Fix (Strategy Design Pattern):

  • Create an abstract class / interface Strategy with methods play() and setScorePoint()
  • Create concrete classes: Attack extends Strategy, Defend extends Strategy
  • Match and Team work through the Strategy abstraction — no if/else needed
  • Adding a new team's strategy = creating a new class, not modifying Match
Strategy Pattern Key Roles:
  • Context (Team/Match): holds a reference to a Strategy; communicates via the interface only
  • Strategy Interface: declares the common method all strategies implement
  • Concrete Strategies (Attack, Defend): implement the actual behavior
L
Liskov Substitution Principle
LSP — Subclasses must be substitutable for their superclasses
Definition: "Objects of a superclass should be replaceable with objects of its subclasses without breaking the system."

Introduced by Barbara Liskov in 1987. If class B extends class A, you should be able to use B anywhere A is expected — and the program still works correctly.

In simple terms: A subclass should not be more restrictive than the behavior defined by the superclass.

⚠️ Warning sign: If an overridden method throws an Exception or does nothing (empty body), you are almost certainly violating LSP.

The Four Conditions for LSP

Condition 1 — Contravariance (Method signatures):

Method parameters in the subclass must be the same as or more generic than the parent's method parameters. (Note: Java does not allow making parameters more generic — it treats this as overloading, not overriding.)

Condition 2 — Preconditions cannot be strengthened:

A subclass method cannot add more conditions/constraints than the parent. Example: if the parent accepts any integer, the child cannot restrict to positive integers only.

Condition 3 — Postconditions cannot be weakened:

The subclass must deliver at least what the parent promises. Example: if the parent closes a DB connection at the end of a method, the child must also close it. Leaving it open weakens the postcondition.

Condition 4 — Exception types must match:

If the parent throws FileNotFoundException, the overriding method must also throw (only) FileNotFoundException — not a different exception type.

Vehicle Example — Violation

Bicycle extends Vehicle but overrides startEngine() by throwing an exception. A bicycle has no engine! When you substitute a Bicycle for a Vehicle in a list and call startEngine(), it crashes.

Vehicle Example — Fixed

Restructure the hierarchy: Vehicle → VehicleWithEngines → Car and Vehicle → VehicleWithoutEngines → Bicycle. Now Bicycle never has a startEngine() method to violate.

Covariant Return Types in Java

Since Java 5, an overriding method can return a subtype of the parent's return type. Example: parent returns Circle, child can return Square if Square extends Circle. This is called covariance.

I
Interface Segregation Principle
ISP — No class should implement methods it doesn't need
Definition (Robert C. Martin): "Clients should not be forced to depend upon interfaces that they do not use."
Analogy: ISP is like SRP applied to interfaces. Just as SRP says a class should have one responsibility, ISP says an interface should be as small as needed — no fat interfaces.

Two rules of ISP:

  • No class should be forced to implement any method of an interface they don't use.
  • Instead of one large "fat" interface, create multiple smaller, focused interfaces.

Printer Example — Violation

PrinterTasks interface has: Print(), Scan(), Fax(), PrintDuplex().

LiquidInkjetPrinter doesn't support Fax or PrintDuplex, but is forced to implement them — and throws UnsupportedOperationException. This also violates LSP!

Printer Example — Fixed

Split into 4 interfaces: PrintingTasks, ScanTasks, FaxTasks, DuplexTasks.

  • HPLaserJetPrinter implements PrintingTasks, ScanTasks, FaxTasks, DuplexTasks
  • LiquidInkjetPrinter implements PrintingTasks, ScanTasks — clean, no unused methods
D
Dependency Inversion Principle
DIP — Depend on abstractions, not concretions
Definition: High-level modules should not depend on low-level modules. Both should depend on abstractions. Abstractions should not depend on details. Details should depend on abstractions.

Store / Payment Example — Violation

Store class directly instantiates Stripe (this.stripe = new Stripe()). The high-level module (Store) is tightly coupled to the low-level module (Stripe). If Stripe goes down and you need PayPal, you must modify the Store class everywhere.

Store / Payment Example — Fixed

Introduce a PaymentGateway interface. Both Stripe and Paypal implement it. Store depends on the interface, not the concrete class. Now switching providers requires zero changes to Store.

Dependency Injection (DI) — The Technique

DI is the mechanism used to implement DIP. Instead of a class creating its own dependencies, they are injected from outside.

DI is a technique; DIP is a principle. DI implements DIP.

Three Types of Dependency Injection

TypeHow it worksWhen to use
Constructor InjectionDependency passed via constructor parameterRequired dependency, same for lifetime of object
Setter InjectionDependency passed via a public setter methodOptional dependency, can change at runtime
Interface InjectionClass implements an injector interface with a setter methodWhen the framework/injector contract must be enforced

Inversion of Control (IoC)

IoC is the general principle of inverting extra responsibilities of a class. DI is one specific way to implement IoC. IoC resolves dependencies at runtime rather than compile time.

Key Relationships — The Big Picture

DI (technique) → implements → DIP (principle) → enables → OCP (principle)
By injecting abstractions, you can add new concrete classes without modifying existing high-level classes — satisfying both DIP and OCP simultaneously.

Smart Summary

S
SRP — Single Responsibility Principle
  • Core rule: One component = one responsibility = one reason to change
  • Component = class, method, or module
  • Cohesion = degree of relatedness within a component → aim for HIGH cohesion
  • Coupling = degree of interdependency between components → aim for LOOSE coupling
  • Square example: Split into Square (math) + SquareUI (rendering)
  • Student example: Split into Student (profile data) + StudentRepository (DB operations)
  • Closely related reasons to change can be combined into one responsibility
O
OCP — Open/Closed Principle
  • Open for extension (add new features) + Closed for modification (don't change existing code)
  • Achieve via interfaces / abstract classes instead of concrete dependencies
  • New behavior → create a new class, don't edit existing ones
  • Reduces risk of introducing bugs to working code
  • Football example: Abstract Strategy class + Attack and Defend subclasses
  • Strategy Pattern: Context → Strategy Interface → Concrete Strategies
L
LSP — Liskov Substitution Principle
  • Subclass objects must be usable wherever superclass objects are expected
  • Introduced by Barbara Liskov (1987)
  • Warning signs: override throws exception OR override does nothing
  • Condition 1 — Contravariance: parameters same or more generic than parent
  • Condition 2 — Preconditions: cannot be strengthened in subtype
  • Condition 3 — Postconditions: cannot be weakened in subtype
  • Condition 4 — Exceptions: same exception type as parent
  • Vehicle fix: VehicleWithEngines + VehicleWithoutEngines hierarchy
  • Covariant return: Java 5+ allows subtype return in overriding method
I
ISP — Interface Segregation Principle
  • Defined by Robert C. Martin while consulting for Xerox
  • Clients should not be forced to depend on interfaces they don't use
  • Fat interfaces → multiple smaller focused interfaces
  • ISP violation often co-occurs with LSP violation (throw UnsupportedOperationException)
  • Printer example: Split PrinterTasks into PrintingTasks, ScanTasks, FaxTasks, DuplexTasks
  • A class implements only the interfaces it actually needs
D
DIP — Dependency Inversion Principle
  • High-level modules should NOT depend on low-level modules — both depend on abstractions
  • Details depend on abstractions, NOT the other way around
  • Implementation technique: Dependency Injection (DI)
  • Three DI types: Constructor, Setter, Interface injection
  • IoC = general concept; DI = one specific IoC implementation
  • Store example: Store → PaymentGateway interface ← Stripe / PayPal
  • DI resolves dependencies at runtime, not compile time
  • Benefits: easier testing, less coupling, easier maintenance and reuse
  • The chain: DI implements DIP, which enables OCP

⚠️ Common Exam Traps

Trap 1: "OCP means you can never change existing code." — Wrong! OCP says don't modify for new features, but bug fixes are allowed.
Trap 2: "LSP only applies to inheritance." — Wrong! It also applies to interface implementations.
Trap 3: "DI and DIP are the same thing." — Wrong! DIP is the principle; DI is the technique used to implement it.
Trap 4: "An overriding method that does nothing is fine." — Wrong! This is a classic LSP violation.
Trap 5: "ISP is just about making interfaces small." — Partially true, but the real reason is: clients should not be forced to depend on things they don't use.
Trap 6: "High cohesion means one method per class." — Wrong! It means all methods in the class are closely related to the same responsibility.
Trap 7: "Covariant return type means the child can return any type." — Wrong! The return type must be a subtype of the parent's return type.

⚡ 10 Things to Remember

  1. SRP: High cohesion, loose coupling = one reason to change
  2. OCP: Abstractions + Strategy Pattern = extend without modifying
  3. LSP: 4 conditions (Contravariance, Pre-, Post-conditions, Exceptions)
  4. LSP warning: throw Exception in override OR empty override = violation
  5. ISP: Robert C. Martin, Xerox — fat interface → many small interfaces
  6. DIP: Both modules depend on abstraction, not on each other
  7. DI ≠ DIP: DI (technique) implements DIP (principle)
  8. IoC: General concept; DI is one form of IoC
  9. Chain: DI → DIP → enables OCP
  10. Java 5+: Covariant return type = child can return subtype of parent's return
