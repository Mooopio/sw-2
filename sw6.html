Topic 01

What is the Cloud?

The cloud is a massive collection of remote servers owned by companies and offered for rent. These are not physical boxes sitting in your room — they are virtual servers, meaning they are created in software (not hardware).

Analogy: Think of the cloud like electricity from the power grid. You don't build your own power plant; you just plug in and pay for what you use. Similarly, you don't buy physical servers; you "plug into" the cloud and rent what you need.
Key Properties
  • Rent as many servers as needed — scale up or down on demand
  • Cloud servers can be started and shut down as demand changes
  • Access from any networked device: laptop, tablet, TV
  • Two models: rent a server and install your own software, OR pay for ready-made cloud software products
Topic 02

Benefits of Cloud for Software Development

Using the cloud instead of private/on-premises servers gives you major advantages:

  • Cost: No upfront capital expense on hardware procurement.
  • Startup Time: Servers can be up and running in minutes, not days/weeks waiting for hardware delivery.
  • Server Choice / Scalability: Easily upgrade to more powerful systems; add servers temporarily for load testing.
  • Distributed Development: Geographically dispersed teams all share the same environment — seamless collaboration, no sync issues.
Topic 03

Physical Servers vs. Virtual Machines

Physical Server: Dedicated to a single user. Has its own OS, memory, hard drive, processor, and network. Expensive and inflexible.

Virtual Machine (VM): Software-simulated computer that acts like a real computer with its own OS. Created using a Hypervisor installed on a physical server.

Analogy: A physical server is like owning a house. A VM is like dividing that house into multiple apartments — same building, but each apartment (VM) has its own rooms (resources), lock (OS), and tenants (applications).
Hypervisor Role A hypervisor is software installed on a physical server that enables creating and managing multiple VMs. Each VM gets its own OS, resources, and server applications. When a VM is used as a server → it's called a Virtual Server.
Topic 04

Container-Based Virtualization

When you have a cloud system running many instances of the same applications (all using the same OS), you can use a lighter and faster alternative to VMs called Containers.

Analogy: If VMs are full apartments with their own kitchens, bathrooms, and walls — containers are like hotel rooms in the same building. The building's infrastructure (OS kernel) is shared, but each room is isolated and self-contained.

OSOwn full OS per VMShares host OS kernel

Benefits of Containerization
  • Portability: Run anywhere Docker is installed — laptop, server, cloud
  • Lightweight: No full OS overhead; much smaller footprint
  • Speed: Start/stop in seconds vs. minutes for VMs
Topic 05

Docker — The Container Engine

Docker is an open-source container management service. It is installed on your OS (Linux preferred, but also Windows/macOS) and enables you to build, run, and manage containers.

Multiple Docker containers can run simultaneously on a single operating system.

Core Docker Terminology
  • Dockerfile: A plain text file with instructions to build an image. Specifies base image, packages, files, and configuration. Automates reproducible image creation.
  • Docker Image: A lightweight, standalone, executable software package containing everything needed to run an application (code, runtime, libraries, settings). Read-only template. Can be versioned and shared via Docker Hub.
  • Docker Container: A running instance of an image. Your application in action, isolated from other containers.
  • Docker Registry: Stores Docker images. Docker Hub is the default public registry. Private registries are also possible.
  • Docker Daemon (dockerd): Background service that listens for Docker API requests and manages images, containers, networks, and volumes. The most critical component — acts as middleman between CLI and containers.
  • Docker Client: The primary interface for users (CLI commands like docker run, docker pull). Sends commands to the daemon via the Docker API.
Dockerfile → Image → Container analogy: A Dockerfile is like a recipe. The Docker Image is like the finished dish photo (read-only). A Container is a serving of that dish that someone is actually eating right now (running instance).

The docker pull command downloads images from a registry (default: Docker Hub). The docker build command creates an image from a Dockerfile. The docker run command starts a container from an image.

Topic 06

Docker Architecture

Docker uses a client-server architecture with these components:

  • Client: Issues commands (docker build, docker pull, docker run)
  • Docker Daemon (DOCKER_HOST): Receives commands, manages all Docker objects
  • Registry: Stores images; daemon fetches images from here

Docker also uses Namespaces to provide the isolated workspace (container). When a container runs, Docker creates a set of namespaces. Each aspect of the container runs in its own namespace — process isolation, network, filesystem, etc.

Topic 07

Can You Run Windows AND Linux Containers Together?

Not natively. Containers share the host OS kernel. Linux containers need a Linux kernel; Windows containers need a Windows kernel. You cannot mix kernels because containers don't emulate OS — they share it.

Workarounds
  • Docker Desktop on Windows: Uses WSL 2 (Windows Subsystem for Linux v2) to run a Linux kernel inside Windows. Can switch between Linux and Windows containers, but not simultaneously.
  • Virtual Machines: Run a Linux VM on a Windows host (for Linux containers) or a Windows VM on a Linux host (for Windows containers).
Topic 08

Everything as a Service (XaaS)

Cloud computing is fundamentally about renting instead of owning. There are three main service models:

ModelWhat you getYou manageVendor manages
IaaSVirtual servers, compute, network, storageApplications, Data, Runtime, Middleware, OSVirtualization, Servers, Storage, Networking
PaaSLibraries, frameworks, SQL/NoSQL DBsApplications, DataEverything below app layer

Pizza Analogy: On-Premises = cook everything at home. IaaS = buy raw ingredients delivered. PaaS = buy a ready pizza kit. SaaS = order from a restaurant and just eat.
Topic 09

SaaS — Advantages & Disadvantages

Advantages for customers:

  • No upfront costs for software or servers
  • Immediate software updates
  • Reduced software management costs
  • Accessible from mobile, laptop, and desktop

Disadvantages / Data Issues:

  • Regulation: EU countries have strict data storage laws that may conflict with the SaaS provider's home country laws.
  • Network Constraints: High data transfer needs may be limited by network speed — problem for smaller companies.
  • Security Concerns: Sensitive data handed to an external provider; even large providers have had breaches.
  • Data Exchange: Difficult to exchange data between cloud services and local apps unless the cloud service provides a public API.
  • Loss of Control: Provider controls when/how software is updated.
  • Service Lock-in: Hard to switch providers once deeply integrated.
Topic 10

SaaS Design Issues

  • Local vs. Remote Processing: Some features run locally in the browser/app (reduces network traffic, speeds up response), some on remote server. Local processing uses more device power.
  • Authentication: Options include own system (extra credentials to remember), OAuth via Google/Facebook/LinkedIn, or federated authentication (delegating to the user's employer).
  • Information Leakage: Multiple organizations on the same platform risk data leaking between tenants. Security design must prevent cross-tenant access.
Topic 11

Multi-Tenant vs. Multi-Instance Systems

Multi-TenantMulti-Instance
DefinitionALL customers share ONE system instance and ONE databaseEach customer gets their OWN copy of system + database
Data separationLogical: tenant identifier tags each recordPhysical: separate DBs per customer
SchemaSingle, shared (defined by provider)Per-instance, customizable
UpdatesOne update reaches all customers simultaneouslyMust update each instance separately
ComplexityHigher (managing many users)Lower per-instance
Multi-Tenant Database Details
  • Database is partitioned — each company has its own "space"
  • All records tagged with a tenant identifier
  • Access software uses tenant ID to provide logical isolation (users feel like they have their own DB)
  • Single schema defined and controlled by the SaaS provider

Multi-Tenant Advantages:

  • Resource utilization: Provider controls and optimizes all resources efficiently
  • Security: Designed for security from scratch; only one DB copy to patch
  • Update management: Single update reaches all customers simultaneously

Multi-Tenant Disadvantages:

  • Inflexibility: All customers use the same schema — limited customization
  • Security risk: Data leak between tenants is theoretically possible; a breach affects ALL customers
  • Complexity: More complex to build and maintain; higher bug risk

  • Dockerfile → text file with build instructions (recipe)

  • Registry → stores images (Docker Hub = default public registry)

  • Data regulation – conflicting laws between countries

⚠️ Common Exam Traps

TRAP: "Containers have their own OS" — WRONG. Containers SHARE the host OS kernel. VMs have their own OS.
TRAP: "A Docker Image is a running application" — WRONG. An IMAGE is a static template. A CONTAINER is the running instance.
TRAP: "Multi-tenant means multiple databases" — WRONG. Multi-tenant = ONE database shared by all customers, logically separated by tenant ID.
TRAP: "Docker can run Windows and Linux containers simultaneously natively" — WRONG. You need WSL2 or VMs, and still can't run both at the exact same time natively.
TRAP: "SaaS gives customers full control over data storage" — WRONG. SaaS customers lose control over data storage location, which creates regulatory problems.
TRAP: "Multi-tenant databases are always more secure than multi-instance" — PARTIALLY WRONG. They are better designed for security, but a breach affects ALL customers at once.
TRAP: "IaaS means you manage nothing" — WRONG. With IaaS, you still manage the OS, middleware, runtime, data, and application.

🔢 Chunking: Numbers to Remember

  • Containers = Megabytes in size | VMs = Gigabytes
  • Containers start in seconds | VMs start in minutes
  • Cloud servers can be up in minutes (vs. days/weeks for physical hardware delivery)
  • Docker is installed on OS; multiple containers run on one OS simultaneously

🔗 Concept Relationships

Understanding HOW concepts connect locks them in memory:

  • Dockerfile is used to BUILD a Docker Image
  • A Docker Image is RUN to create a Docker Container
  • Images are stored in and retrieved from a Docker Registry
  • The Docker Client sends commands to the Docker Daemon
  • The Daemon manages Images, Containers, Networks, and Volumes
  • Namespaces → isolation mechanism used inside containers
  • VMs use a Hypervisor; Containers use Docker Engine
  • SaaS uses multi-tenant or multi-instance architecture for serving customers
