Clean Code

A thorough, exam-optimized breakdown of every concept — Meaningful Names, Functions, Objects & Structures.

13 Naming Rules Functions Objects vs Data Law of Demeter Abstraction

What is Clean Code?

Think of code like a book. Working code means the book exists and has all its pages. Clean code means any developer can pick it up, read it fluently, and modify it without confusion. Good code = Working + Clean.

📌 Core Definition
  • Clean Code — Readable, maintainable, extendable
  • Working Code — Does what it is supposed to do
  • Good Code — The combination of both

Martin Fowler's famous quote: "Any fool can write code that a computer can understand. Good programmers write code that humans can understand."

⚠️ The WTF/Minute Rule

A good measure of code quality is how many "WTF" moments a reviewer has per minute. Your goal: reduce WTFs to nearly zero. Strategies: peer review, consistent standards, continuous practice.

🏷️ PART 1 — Meaningful Names (13 Rules)

01

Use Intention-Revealing Names

The name of a variable, function, or class must answer three questions: Why does it exist? What does it do? How is it used? If you need a comment to explain the name, the name is wrong.

❌ Bad
public List<int[]> getThem() {
  List<int[]> list1 = new ArrayList<>();
  for (int[] x : theList)
    if (x[0] == 4) list1.add(x);
  return list1;
}

❓ What is theList? What is x[0]? Why 4? What is returned?

✅ Good (Step 1)
public List<int[]> getFlaggedCells() {
  List<int[]> flaggedCells = new ArrayList<>();
  for (int[] cell : gameBoard)
    if (cell[STATUS_VALUE] == FLAGGED)
      flaggedCells.add(cell);
  return flaggedCells;
}
✅✅ Better (Step 2 — with Cell class)
public List<Cell> getFlaggedCells() {
  List<Cell> flaggedCells = new ArrayList<>();
  for (Cell cell : gameBoard)
    if (cell.isFlagged()) flaggedCells.add(cell);
  return flaggedCells;
}

Same operators, same logic — but now it reads like English!

02

Avoid Disinformation

Don't leave false clues. Avoid reserved keywords in names, ambiguous words, and names that differ only slightly.

  • Never use l (lowercase L) or O (uppercase O) as variable names — they look like numbers 1 and 0
  • Avoid nearly-identical names: XYZControllerForEfficientHandlingOfStrings vs XYZControllerForEfficientStorageOfStrings
❌ Classic Trap
int a = l; // is l a 1 or the letter l?
if (O == l) { a = O1; } // O is zero or letter O?
03

Use Meaningful Distinctions

If two names must differ, they must also mean something different. Number-series names like a1, a2, a3 carry zero information.

❌ Bad
public static void copyChars(char a1[], char a2[]) { ... }
✅ Good
public static void copyChars(char source[], char destination[]) { ... }
04

Eliminate Noise Words

Noise words add nothing. Examples: NameString — why not just Name? theAccount vs account? ProductData vs Product?

  • Never use "variable" in a variable name
  • Never use "table" in a table name
  • Never use "String", "Data", "Info", "Object" as suffixes
05

Use Searchable Names

Magic numbers are unfindable. If you search for 7, you'll get thousands of hits. If you search for NUMBER_OF_SUBJECTS, you find exactly what you need.

❌ Bad
for (int j=0; j<7; j++) { s += t[j]; }
✅ Good
int NUMBER_OF_SUBJECTS = 7;
int TotalGrade = 0;
for (int j=0; j<NUMBER_OF_SUBJECTS; j++)
  TotalGrade += Student_grade[j];
📌 Rule

Single-letter names ONLY inside short methods. The length of a name ∝ the size of its scope.

06

Class Names — Answer "WHO?"

Classes and objects should be nouns or noun phrases: Customer, WikiPage, Account, AddressParser.

  • Avoid words like: Manager, Processor, Data, Info
  • A class name should never be a verb
07

Method Names — Answer "WHAT does it do?"

Methods should be verbs or verb phrases: postPayment(), deletePage(), save().

📌 Static Factory Methods

When constructors are overloaded, use static factory methods with descriptive names:

Address.createShortAddress(1, "tahrir", "helwan");
Address.createFullAddress(1, 4, 4, "tahrir", "helwan", "cairo", "Egypt");

Better than: new Address(1, "tahrir", "helwan") — you have no idea what the args mean!

08

Avoid Encodings (Hungarian Notation)

Hungarian Notation adds type prefixes to names: iAge, strName, lCount. Microsoft banned it in 2008.

  • Modern IDEs already show types — prefixes are redundant
  • When you change the type, you must rename — fragile!
  • Makes code noisier and harder to read the meaningful part
  • Interfaces: prefer ShapeFactory over IShapeFactory. If you must encode, name the implementation: ShapeFactoryImp
09

Use Pronounceable Names

If you can't say it out loud, you can't discuss it in a team meeting without sounding foolish. Programming is a social activity.

❌ Bad
class DtaRcrd102 {
  private Date genymdhms;
  private Date modymdhms;
  private final String pszqint = "102";
}
✅ Good
class Customer {
  private Date generationTimestamp;
  private Date modificationTimestamp;
  private final String recordId = "102";
}
10

Avoid Mental Mapping

Don't force readers to mentally translate r → "full URL of Dacia server from Romania." Clarity beats cleverness.

Exception: well-known conventions like i, j for loop iterators are fine because every programmer already knows them.

11

Don't Be Cute

Clever names are only funny to those who share the author's humor — and only while they remember the joke.

  • Don't use whack() to mean kill()
  • Don't use eatMyShorts() to mean abort()
  • Say what you mean. Mean what you say.
12

Pick One Word Per Concept

Choose one word for one abstract concept and stick with it across the entire codebase.

❌ Inconsistent✅ Consistent
getArticles()
fetchUsers()
retrievePages()		getArticles()
getUsers()
getPages()

Having controller, manager, and driver in the same codebase is also confusing — they all mean the same thing.

13

Add Meaningful Context

Seeing state alone is ambiguous — is it a boolean state? A US state? But addrState next to addrFirstName, addrCity, addrCountry clearly forms an address.

Use prefix context: addr, user, order, etc. Or better yet, wrap variables in a well-named class.

⚙️ PART 2 — Clean Functions

Rule 1: Keep Functions Small

"The first rule of functions is that they should be small. The second rule of functions is that they should be smaller than that." — Robert C. Martin

  • Any method longer than ~10 lines should raise questions
  • Use Extract Method refactoring to split long methods

Rule 2: Do One Thing (SRP for Functions)

  • Functions Should Do One Thing
  • Functions Should Do It Well
  • Functions Should Do It Only
💡 How to check

Try to extract another function with a different name from inside your function. If you can, the original function is doing more than one thing.

The refactoring example: addDataToFile() was doing reading, adding, writing, AND printing. After refactoring:

// Each function does exactly ONE thing:
readDataFromFile(path)
addDataToList(person, people)
addDataToFile(path, people)     // only writes!
PrintPersonDataFile(people)    // only prints!

Rule 3: One Level of Abstraction Per Function (SLAP)

All statements inside a function must be at the same level of abstraction. Don't mix high-level calls with low-level implementation details.

❌ Mixed Levels — Confusing
printNumbersOneToThirtyFive() {
  printNumbersOneToTen(); // high-level
  for(int i=11; i<21; i++) System.out.println(i); // low-level!
  System.out.println(21); // micro-detail!
  // ...deep nested ifs and loops...
}
✅ Same Level — Clean
printNumbersOneToThirtyFive() {
  printNumbersOneToTen();
  printNumbersElevenToTwenty();
  printNumberTwentyOne();
  printNumbersTwentyTwoToThirtyFive();
}

Rule 4: Fewer Arguments

Arguments increase cognitive load. Preference order: 0 > 1 > 2 > 3+

  • Try to avoid 3-argument functions
  • Never use 3+ arguments — use a Request/Parameter object instead
  • You can eliminate arguments by making them class fields
// Bad — too many args:
sendRequest(String ip, int port, String user, String password, String body);
// Good — encapsulate into object:
sendRequest(Request request);

Rule 5: No Flag Arguments

Passing a boolean to a function is terrible practice. It means the function is doing two things depending on the flag.

❌ Bad
void printAddress(Boolean isLong) {
  if(isLong) { /* long address */ }
  else { /* short address */ }
}
✅ Good — Split it
void printShortAddress() { ... }
void printLongAddress() { ... }

Rule 6: Keep Blocks Small (1 line each)

The body of if, else, while should ideally be one line — a function call. This prevents deep nesting (max 1–2 indent levels) and adds self-documenting names.

Rule 7: Replace Conditional with Polymorphism

Repeated switch or if-else chains based on a type violate the Open/Closed Principle (open for extension, closed for modification).

❌ Bad — Adding a new vehicle type requires modifying ALL switch statements
switch(type) {
  case BICYCLE: return ParkingSpotSize.SMALL;
  case BIKE: return ParkingSpotSize.MEDIUM;
  // ...repeated in every method!
}
✅ Good — Interface + polymorphism
public interface Vehicle {
  ParkingSpotSize spaceRequiredForParking();
  BigDecimal parkingCharges();
}
public class Car implements Vehicle {
  public ParkingSpotSize spaceRequiredForParking() { return LARGE; }
  public BigDecimal parkingCharges() { return BigDecimal.valueOf(50.00); }
}

New vehicle? Just add a new class — nothing else changes.

🏗️ PART 3 — Objects & Data Structures

Data Abstraction

Abstraction is NOT just making variables private and adding getters/setters. That's just accessors — it exposes the internal structure through thin methods.

True abstraction provides abstract interfaces that let users manipulate data without knowing its implementation.

❌ Concrete (NOT abstraction)✅ Abstract (True abstraction)
getGallonsOfGasoline()
getGallonsNeeded()		getPercentFuelRemaining()

The abstract version hides whether fuel is measured in gallons, liters, or kilowatt-hours.

Data/Object Anti-Symmetry

  • Objects: hide data (private), expose behavior (methods)
  • Data Structures: expose data (public), have no behavior
Add New FunctionAdd New Type
Procedural (Data Structs)✅ Easy❌ Hard (all functions change)
OOP (Objects)❌ Hard (all classes change)✅ Easy
📌 When to use which?
  • Use OOP in complex systems — you'll add more data types than functions
  • Use Procedural when you need to add new functions more often than new types

Law of Demeter (LoD) — "Don't Talk to Strangers"

A module should not know about the inner workings of the objects it manipulates. Method M of class C should only call methods of:

  1. C itself
  2. Parameters passed to M
  3. Objects created inside M
  4. Direct component objects of C (fields)
  5. Global/static variables accessible in M
❌ Violation — Train Wreck / Chained Call
employee.getDepartment().getManager().approveExpense(expenses);

employee knows about Department; Department knows about Manager. Employee is talking to a stranger (Manager).

✅ Fix — Employee talks only to its own friend (Manager injected via constructor)
class Employee {
  private Manager manager;
  Employee(Manager manager) { this.manager = manager; }
  void submitExpense(Expenses expenses) {
    manager.approveExpense(expenses); // manager is a direct field
  }
}
// Usage:
emp.submitExpense(expenses); // clean, loosely coupled

⚠️ Common Exam Traps & Mistakes

  • Trap 1: "Private variables + getters/setters = abstraction" — ❌ WRONG! That's just accessors.
  • Trap 2: "Hungarian Notation is good because it shows the type" — ❌ WRONG! Microsoft banned it. Modern IDEs show types.
  • Trap 3: "A single-letter variable is always bad" — ❌ Not quite! i, j are fine as loop counters in short methods.
  • Trap 4: "Procedural code is always worse than OOP" — ❌ WRONG! It's better when adding new functions frequently.
  • Trap 5: "The Law of Demeter just means avoid chained calls" — Partially right. The rule is specifically about what methods you're allowed to call.
  • Trap 6: "Flag arguments are OK if the boolean is well-named" — ❌ WRONG! It still means the function does two things.
  • Trap 7: "Adding number series (a1, a2) is at least better than nothing" — ❌ WRONG! It's non-informative, not just uninformative.

🔑 THE GOLDEN RULE OF CLEAN CODE
"Any fool can write code a computer understands.
Good programmers write code humans understand."
Good Code = Clean Code + Working Code

13 Naming Rules

  • ✅ Intention-revealing (no comments needed)
  • ❌ No disinformation (not l, O, misleading)
  • ✅ Meaningful distinctions (source, dest)
  • ❌ No noise (NameString → Name)
  • ✅ Searchable (constants, not 7)
  • ✅ Class = Noun (Customer, Account)
  • ✅ Method = Verb (save, deletePage)
  • ❌ No encodings (no iAge, strName)
  • ✅ Pronounceable (generationTimestamp)
  • ❌ No mental mapping
  • ❌ Don't be cute (kill() not whack())
  • ✅ 1 word/concept (get OR fetch, never both)
  • ✅ Context (addrState, addrCity)

Function Rules

  • Small (<10 lines ideal)
  • Do ONE thing only
  • SLAP — one abstraction level
  • Fewer args (0>1>2>3+)
  • No flag (boolean) arguments
  • Blocks = 1 line (function call)
  • Polymorphism over switch/if

Objects vs Data Structures

  • Objects: hide data, expose behavior
  • Data Structs: expose data, no behavior
  • OOP → easy to add types
  • Procedural → easy to add functions
  • Abstraction ≠ getters/setters
  • Abstract = hide implementation details

Law of Demeter

  • "Don't talk to strangers"
  • M() can call: C, params, created-in-M, C's fields, globals
  • Chained calls = violation
  • a.b().c().d() = train wreck
  • Fix: inject dependency via constructor
  • Goal: loose coupling

Key Definitions

  • SLAP = Single Level of Abstraction Principle
  • LoD = Law of Demeter = Principle of Least Knowledge
  • OCP = Open/Closed Principle (switch violates it)
  • Hungarian = Notation with type prefixes (banned)
  • Noise word = redundant word in a name
  • Train wreck = chained method calls violating LoD

Common Traps in Exam

  • getters/setters ≠ abstraction
  • Hungarian Notation is BAD (banned 2008)
  • i, j are OK as loop counters
  • Procedural ≠ always bad
  • Boolean arg = 2 functions, not 1
  • LoD = 5 allowed call types
  • Interface name: ShapeFactory not IShapeFactory
