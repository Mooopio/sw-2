Object Constraint Language

A complete, deeply explained study guide covering MDE, modeling languages, OCL syntax, constraints, and collection operations — structured for exam success.

1. The Three Types of Models

Before understanding OCL, we need to understand Model-Driven Engineering (MDE) and why models matter. Any model falls into one of three categories:

TypePurposeKey WordExample
PredictiveAnalyze the past to predict the futureForecastWeather prediction, sales forecasting
DescriptiveDescribe relationships and group dataGroupingCustomer segmentation, clustering
PrescriptiveMake decisions based on all elementsPrescribe/DecideRoute optimization, resource allocation
Exam Tip

MDE uses Prescriptive models as programs — they actively make decisions. Don't confuse with predictive (past→future) or descriptive (grouping).

2. Model-Driven Engineering (MDE)

MDE is about using prescriptive models as programs. Instead of writing everything in low-level code, engineers work at a higher abstraction level using models.

🔧 What MDE Involves

  • Engineering domain-specific languages (DSLs) for capturing models
  • Defining precise abstract syntax for the language
  • Supporting graphical and textual modeling tools
  • Expressing and checking validity constraints for models
  • Analyzing and simulating models
  • Transforming models into other models or software products

❓ Why MDE? — The Real Reasons

  • Implementation-level abstractions are not satisfactory for complex domains
  • Engineers copy/paste boilerplate code repeatedly (see ATM example below)
  • To make one change, engineers must modify several inter-related artifacts
  • Reasoning about system properties is too hard at implementation level
Real Example 1: Boilerplate Code

An ATM class with a screen attribute requires writing a getter, setter, constructor, and error handling manually. MDE tools like Visual Paradigm generate this boilerplate from a simple model diagram automatically.

Real Example 2: Property Analysis

A traffic light switch statement in code is hard to analyze. A state machine model makes the color transitions visually obvious and allows automated reachability analysis — impossible at the code level for large systems.

3. Modeling Languages & DSLs

There are many off-the-shelf modeling languages. Each focuses on a specific class of domains:

Sometimes existing languages lack appropriate abstractions for a specific problem — this is where Domain-Specific Languages (DSLs) come in. Example: A conference organization system needs its own language to model tracks, talks, speakers, breaks, etc.

4. Why UML Alone Is Not Enough

UML gives us structural and behavioral diagrams, but it cannot express constraints precisely. For example, how do you say in a UML diagram: "parallel tracks must be in different rooms"?

Key Decision

We need a specification add-on, not a brand-new language. Candidates considered:

  • First-Order Logic — too mathematical, not OO-friendly
  • OCL — object-oriented, standardized, widely adopted ✅

5. What Is OCL?

OCL (Object Constraint Language) is a formal language used to specify constraints on object-oriented systems. It is part of the UML standard.

  • First developed in 1995 as IBEL by IBM's Insurance division
  • Used to define UML 1.2 itself
  • Backed by major companies: Rational, Microsoft, IBM, Oracle, HP, etc.
  • It is the only standardized OO constraint language

Where Can OCL Be Used?

  • Specify invariants for classes and types
  • Specify pre- and post-conditions for operations
  • As a navigation language to traverse associations
  • To constrain operations
  • As test requirements and specifications

Advantages of OCL / Formal Constraints

  • Better documentation — adds information beyond what diagrams show
  • More precision — formal semantics reduce ambiguity in UML
  • Communication without misunderstanding — unambiguous between developers

6. Core OCL Concepts: Invariants, Context & Self

Invariant

A constraint (invariant) is a boolean OCL expression that must always evaluate to true. It is a rule that must never be violated.

Context

Every constraint is bound to a specific type/class in the UML model — this is its context. Written as:

context <ClassName> invariant [optionalName]: <boolean expression>

Self

self refers to the current instance of the context class — like this in Java. It can be omitted (implicit).

context Mortgage invariant: self.startDate < self.endDate -- Same as: invariant: startDate < endDate

7. Types of OCL Constraints

TypeWhen It HoldsKeyword
InvariantAlways — must hold at all timesinvariant
Pre-conditionBefore an operation executespre
Post-conditionAfter an operation executespost

context Company::hire(p : Person) pre hirePre1: p.isDefined() pre hirePre2: employee->excludes(p) post hirePost: employee->includes(p) context Company::fire(p : Person) pre firePre: employee->includes(p) post firePost: employee->excludes(p)
Post-condition Special: @pre

In post-conditions, @pre refers to the value of an attribute before the operation executed.

-- After burn(i), points decreases by i post: points = points@pre - i

8. Navigation in OCL

OCL expressions navigate associations to reach related objects. Starting from the context object, you follow role names:

-- Navigate from CustomerCard to its owner (Customer) context CustomerCard invariant: owner.age >= 18 -- owner is a Customer; .age is an Integer

Navigation Across Multiplicity > 1 → Collections

When navigating an association with many multiplicity (0..*), you get a Collection. Use -> to call collection operations:

context CustomerCard invariant: owner.Membership->includes(membership) -- owner.Membership is a Set of Membership instances
Common Trap

Use . (dot) to access attributes/operations on a single object. Use -> (arrow) to call collection operations. Mixing them is a common exam mistake.

9. OCL Collections

OCL has a rich collection type system. Collection is the parent type. Operations on collections never change the original — they return new collections.

Illustrated Examples

Exam Note on implies

A implies B is only false when A is true and B is false. If A is false, the whole expression is true regardless of B.

Why DSLs?

4. OCL — Key Facts

  • Object Constraint Language — part of UML standard
  • Developed 1995 by IBM as IBEL
  • Used to define UML 1.2 itself
  • Only standardized OO constraint language
  • Benefits: Better docs, more precision, no misunderstanding

5. OCL Constraint Types

  • Invariant — always true
  • Pre-condition — before operation
  • Post-condition — after operation; use @pre for old values
  • Guard — state machine transition

6. Navigation Rules

  • Dot (.) → single object attribute or operation
  • Arrow (->) → collection operation
  • Navigate role names along associations from self
  • Navigating multiplicity > 1 → returns a Collection
  • context keyword sets the class; self = current instance

7. Collection Types

  • Set — no duplicates, unordered (default single navigation)
  • Bag — duplicates allowed, unordered (multi-step navigation)
  • Sequence — duplicates allowed, ordered
  • OrderedSet — no duplicates, ordered
  • Convert: ->asSet(), ->asBag(), ->asSequence()

8. Critical Collection Operations

Boolean Tests

  • isEmpty() / notEmpty()
  • includes(obj) / excludes(obj)
  • includesAll(col)
  • forAll(cond)
  • exists(cond)

Transformations

  • size() → count
  • sum() → total
  • count(obj) → occurrences
  • select(cond) → filter in
  • reject(cond) → filter out
  • collect(expr) → transform

9. OCL Syntax Template

context ClassName invariant [name]: <boolean-expression> context ClassName::operation(param: Type) pre [name]: <precondition> post [name]: <postcondition using @pre if needed> -- Navigation self.role.attribute -- dot for single object self.roles->operation() -- arrow for collection

10. Logical Connectives

and · or · not · implies · xor

implies: only false when left=true AND right=false
