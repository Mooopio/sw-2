1. The Problem with OOP

Before AOP, understand what OOP failed to solve.

The Core Pain

In OOP, when you have cross-cutting concerns (like logging, security, transactions), you're forced to scatter the same code across every class. Imagine writing LogMessage() inside Class A, Class B, and Class C — that's pure code duplication.

🔴 Code Tangling ▼

Code Tangling happens when a single module tries to handle multiple concerns at once — your core business logic is tangled up with logging, security, and transaction code in the same methods.

Analogy: Imagine a chef who simultaneously cooks, writes the order, cleans the table, and processes payment — all in one motion. That's tangled code.

Hard to read
Confuses responsibilities
Breaks Single Responsibility Principle
🔴 Code Scattering ▼

Code Scattering is the mirror problem: the same concern (e.g., logging) is duplicated across many different modules. If you need to change how logging works, you must update every class.

Analogy: The fire alarm system in a building — instead of one central panel, imagine every room having its own separate alarm wired differently. Changing the system means going room by room.

Violates DRY principle
High maintenance cost
Bug-prone updates

Problems in OOP (4 Key Problems)

1. Poor Traceability ▼

When multiple concerns live in the same module, it becomes impossible to trace which code addresses which requirement. You can't easily answer: "Where exactly is my login security implemented?"

This breaks the link between requirements and their implementation.

2. Lower Productivity ▼

Developers waste time on peripheral issues (security, logging, transactions) instead of the actual problem domain. Every new class needs boilerplate repeated — attention is drained from real work.

3. Less Code Reuse ▼

Boilerplate code is propagated through cut-and-paste — there is no real code reuse. Every copy is a risk: if the original is buggy, all copies are buggy too.

4. Harder Refactoring ▼

Changing a requirement means touching many modules for a single concern. Want to add a timestamp to every log? Update 30 classes. This is painful and error-prone.

2. Understanding Concerns

Definition

Concerns are NOT just program issues — they reflect system requirements and the priorities of stakeholders. A concern is anything the system must address: performance, security, specific functionality, etc.

By reflecting separation of concerns in code, you get clear traceability from requirements to implementation.

Types of Concerns

Concern Type Description Example
Core Concerns Functional concerns related to the primary purpose of the system Processing a bank transaction
Secondary Concerns Functional concerns reflecting non-functional requirements Performance, logging
Functional Concerns Specific functionality to include in the system User authentication
Quality of Service Non-functional behavior of the system Response time, availability
Policy Concerns Overall policies governing system use Access control policies
System Concerns Attributes of the system as a whole Maintainability, configurability
Organisational Concerns Organisational goals and priorities Delivering within budget

3. AOP — The Solution

Core Idea

Aspect-Oriented Programming (AOP) solves code tangling and scattering by centralizing cross-cutting concerns into separate modules called Aspects. Instead of every class having LogMessage(), a single Logging Aspect handles it for all classes automatically.

Benefits of AOP

  • Centralize concern implementation — one place for each cross-cutting concern
  • Intercept method calls — execute code before/after methods transparently
  • Inject new behavior — add functionality without changing existing code
  • More reusable code — write once, apply everywhere
  • Cleaner code — each module focuses on its primary responsibility
  • Write less code — no more copy-paste boilerplate
  • More maintainable — change one Aspect, affects all join points

4. AOP Core Terminologies

These are the most exam-critical definitions. Know every one cold.

🟢 Aspect ▼

An Aspect is a class that implements enterprise application concerns that cut across multiple classes — such as transaction management, logging, security.

In Spring Framework, Aspects can be:

  • Configured through Spring XML configuration
  • Defined using @Aspect annotation via Spring AspectJ integration

Analogy: An Aspect is like a universal plugin you plug into your application — it automatically handles a concern wherever it's needed, without the classes knowing about it.

@Aspect public class LoggingAspect { // Handles logging for all classes }
🟢 Join Point ▼

A Join Point is a specific point in the application such as:

  • Method execution
  • Exception handling
  • Changing object variable values

⚠️ Exam Trap: In Spring AOP specifically, a join point is always the execution of the method. Spring does NOT support field-level or constructor join points like AspectJ does.

Analogy: A join point is like a bus stop — it's a defined location where something could happen (a bus could stop there).

🟢 Advice ▼

Advice is the action taken for a particular join point. It is the actual code that runs when the aspect is triggered.

Think of it as: "When X happens (join point), do Y (advice)."

Analogy: Continuing the bus analogy — if a join point is a bus stop, Advice is what happens when the bus actually stops there (passengers board, doors open, etc.).

🟢 Point Cut ▼

A Point Cut is an expression matched with join points to determine whether advice needs to be executed or not. It identifies the specific events with which advice should be associated.

Key insight: AOP's ability to multicast the same aspects into many places in your code is called Point Cut.

// All methods in com.tutorialspoint package @Pointcut("execution(* com.tutorialspoint.*.*(..))") // Only Student.getName() method @Pointcut("execution(* com.tutorialspoint.Student.getName(..))")

Analogy: A Point Cut is like an employee schedule filter — it says "advice applies to ALL methods" or "only to THIS specific method."

🟢 Weaving ▼

Weaving is the process that combines advice with point cuts. It is the incorporation of advice code at the specified join points by an aspect weaver.

The weaver is the engine that makes AOP work — it takes your Aspect definitions and "weaves" them into the regular code at the right moments.

Analogy: Weaving is like a tailor (the weaver) who takes a plain shirt (your code) and sews in special patches (aspects) at specific locations (join points), without you having to redesign the shirt.

5. AOP Advice Types (5 Types)

The 5 advice types are extremely high-yield for exams. Know each annotation.

1. Before Advice — @Before ▼

Runs before the execution of the join point method. Used for logging before a method call, security checks, parameter validation.

@Before("execution(* com.example.*.*(..))") public void beforeAdvice(JoinPoint joinPoint) { System.out.println("Before: " + joinPoint.getSignature()); }
2. After (Finally) Advice — @After ▼

Executes after the join point method finishes, whether it finished normally or by throwing an exception. It's like a finally block in Java — it always runs.

⚠️ Exam Trap: @After runs regardless of success/failure. Don't confuse with @AfterReturning (only on success) or @AfterThrowing (only on exception).

3. After Returning Advice — @AfterReturning ▼

Executes only if the join point method executes normally (no exception). Useful for processing the return value, success-only logging.

Use when you need to take action only upon successful completion.

4. After Throwing Advice — @AfterThrowing ▼

Executes only when the join point method throws an exception. Very useful for declarative rollback of transactions or exception-specific logging.

This lets you centralize exception handling logic across all methods.

5. Around Advice — @Around ⭐ Most Powerful ▼

Around Advice is the most important and powerful advice type. It surrounds the join point method completely. Key capabilities:

  • Runs code before the join point
  • Can choose whether to execute the join point method at all
  • Runs code after the join point
  • Is responsible for invoking the join point method
  • Must return values if the method returns something
@Around("execution(* com.example.*.*(..))") public Object aroundAdvice(ProceedingJoinPoint pjp) throws Throwable { System.out.println("Before method"); Object result = pjp.proceed(); // Execute the method System.out.println("After method"); return result; }

6. AOP Configuration Concept

When configuring AOP, you answer 4 key questions:

  • Which Aspect? — Which cross-cutting concern to apply (Logging, Security, Transaction)?
  • Which Class? — Which target class to intercept?
  • Which Method? — Which specific method(s) within that class?
  • Which Position? — Before, After, Around, AfterReturning, or AfterThrowing?

⚠️ Common Exam Traps

Trap 1 — Join Point in Spring AOP

In Spring AOP, a Join Point is ALWAYS method execution. Not field access, not constructor calls. If an exam option says "field change" or "constructor call," it's a trap — that's AspectJ, not Spring AOP.

Trap 2 — @After vs @AfterReturning vs @AfterThrowing

  • @After = ALWAYS runs (success OR exception) — like finally{}
  • @AfterReturning = ONLY on success (no exception)
  • @AfterThrowing = ONLY on exception

Trap 3 — Around Advice Responsibility

With @Around, you are responsible for calling pjp.proceed() to execute the target method. If you forget it, the actual method never runs. It must also return the value.

Trap 4 — Code Tangling vs Code Scattering

  • Tangling = MULTIPLE concerns in ONE module
  • Scattering = ONE concern in MULTIPLE modules

These are opposites but both are problems of cross-cutting concerns in OOP.

Trap 5 — Concerns ≠ Code Problems

Concerns reflect system requirements and stakeholder priorities — not just code-level issues. An organisational concern like "deliver within budget" IS a valid system concern even if it's not a class.

📦 Chunking — The AOP "Recipe"

Think of AOP as a recipe with 3 ingredients:

  • What to do? → Advice (the code to run)
  • Where to do it? → Point Cut (the selector expression) → targets specific Join Points
  • Who packages it? → Aspect (the module containing advice + pointcut)
  • Who applies it? → Weaving (the process of injecting advice into join points)
